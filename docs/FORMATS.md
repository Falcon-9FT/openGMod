# Форматы

Описания написаны по открытым источникам (Valve Developer Community wiki, вики GMod,
описания сообщества) и проверены на настоящих файлах. Все числа — little endian, строки — с
нулевым байтом в конце, если не сказано иное.

## VPK — паки Valve

Контент GMod и HL2 лежит в паках: `garrysmod/garrysmod_dir.vpk` и `sourceengine/hl2_*_dir.vpk`.
Пак состоит из файла-каталога `<имя>_dir.vpk` и файлов данных `<имя>_000.vpk`, `<имя>_001.vpk`
и так далее. Небольшой пак может держать данные в самом каталоге.

| Часть | Содержимое |
|---|---|
| заголовок v1 (12 байт) | `u32` сигнатура `0x55AA1234`, `u32` версия, `u32` размер дерева |
| заголовок v2 (28 байт) | v1 + `u32` размеры: встроенных данных, MD5 архивов, прочих MD5, подписи |
| дерево | расширения → папки → имена файлов, у каждого файла — запись |
| встроенные данные | байты файлов с индексом архива `0x7FFF` |

Дерево — три вложенных списка строк (расширение, папка, имя), каждый заканчивается пустой
строкой. Пробел `" "` значит «нет» (файл без расширения или в корне).

Запись файла:
* `u32` CRC-32 всего файла;
* `u16` число preload-байтов, которые идут сразу после записи;
* `u16` индекс архива (`0x7FFF` — сам каталог, отсчёт от конца дерева);
* `u32` смещение;
* `u32` длина;
* `u16` терминатор `0xFFFF`.

Файл — это его preload-байты, за которыми идут `длина` байт по `смещению` в своём архиве.

Реализация: `gmod-fs::vpk`. Проверена на тестовых паках ValvePak, собранных инструментами
Valve: многотомных, однофайловых, с preload, подписанных v2 из CS2.

## GMA — аддоны GMod

| Часть | Содержимое |
|---|---|
| заголовок | `"GMAD"`, `u8` версия формата (1–3) |
| | `u64` SteamID автора (не используется), `u64` время упаковки (Unix) |
| | версия ≥ 2: имена требуемого контента до пустой строки (на практике пусто) |
| | название, описание (в современных аддонах — JSON с `description`, `type`, `tags`), автор, `i32` версия аддона |
| список файлов | `u32` номер (1, 2, …; 0 — конец), путь, `i64` размер, `u32` CRC-32 |
| данные | байты файлов подряд в порядке списка |
| хвост | `u32` CRC-32 всего предыдущего (0, если упаковщик не считал) |

Реализация: `gmod-fs::gma` (чтение и запись). Обрезанный файл (оборванная загрузка) —
ошибка, а не «сколько успели прочитать».

## Воркшоп

* Подписки Steam хранит в `<библиотека>/steamapps/workshop/content/4000/<id>/`: там `.gma`
  или, у предметов из старого воркшопа, `<имя>_legacy.bin`.
* Список установленных — `steamapps/workshop/appworkshop_4000.acf` (KeyValues,
  `AppWorkshop/WorkshopItemsInstalled/<id>`). Папки предметов, которых в списке нет, не
  монтируются.
* `.bin` — это LZMA-поток в контейнере «alone» вокруг GMA:
  * 13 байт заголовка: байт свойств `(pb·5 + lp)·9 + lc`, `u32` размер словаря, `u64` размер
    распакованного (все единицы — неизвестен, тогда в конце стоит маркер);
  * затем сам поток.

  Декодер написан по спецификации LZMA SDK (public domain): `gmod-fs::lzma`. Распакованный
  GMA кладётся в `~/.opengmod/cache/workshop/<id>.gma` и используется, пока он не старше `.bin`.
* `garrysmod/cache/workshop/*.gma` — аддоны, которые скачали серверы. GMod монтирует их только
  на этих серверах, поэтому по умолчанию они не подключаются (`--server-downloads` в
  `gmod-check`).
* `garrysmod/addons/*.gma` — аддоны, положенные вручную.

## KeyValues

Текстовый формат Valve: `gameinfo.txt`, `.vmt`, скрипты в `scripts/`, VGUI `.res`,
локализация, `cfg/mount.cfg`, `.vdf` и `.acf` Steam. Правила токенизатора, как у движка:

* токен — строка в кавычках, `{`, `}` или последовательность символов до пробела, `"`, `{`, `}`;
* `//` — комментарий только там, где может начаться токен (`1//x` — один токен);
* escape-последовательности по умолчанию выключены: в материалах пути пишутся с `\`. Включены в
  файлах Steam и в локализации, где кавычки пишутся как `\"`;
* токен с `[` … `]` — условие для соседней пары (`[$WIN32]`, `[!$X360]`, `[$WINDOWS||$OSX]`).
  `$WIN32` означает любой ПК, консольные символы не определены;
* ключи сравниваются без учёта регистра ASCII и могут повторяться, порядок сохраняется;
* `#base` / `#include` на верхнем уровне — ссылки на другие файлы;
* NUL-байт заканчивает текст; UTF-16 с BOM (файлы локализации) декодируется;
* при ошибке движок закрывает текущий блок и читает дальше. Пустой ключ обрывает блок,
  ключ без значения получает пустую строку, а на верхнем уровне за ключом обязан идти `{`.

Не KeyValues, хотя и `.txt`: `scripts/sentences*.txt`, `scripts/hudanimations*.txt` (кроме
манифеста), `scripts/talker/*`, `scripts/dsp_presets.txt`, а также `.cfg` (это консольные
команды).

Реализация: `gmod-kv`.

## Схемы VGUI и раскладка HUD

Схемы — `resource/SourceScheme.res`, `ClientScheme.res`, `ChatScheme.res` — это KeyValues, в
корневом блоке которых:

* `Colors` — именованные цвета, `"r g b a"` (`a` можно не писать — 255);
* `BaseSettings` — цвета элементов (`FgColor`, `BgColor`, `FgColorHud`, `DamagedFg`...): цвет
  или имя цвета из `Colors` или из самого `BaseSettings`;
* `Fonts` — шрифты по именам (`Default`, `HudNumbers`, `Trebuchet24`...). Шрифт — блок
  вариантов (`"1" { ... }`, `"2" { ... }`): `name` (семейство), `tall` (высота ячейки в
  пикселях, вместе с выносными элементами), `weight`, флаги `antialias`, `additive`,
  `dropshadow`, `outline`, `italic`, `underline`, `strikeout`, `symbol` (0 или 1), `blur` и
  `scanlines` (в пикселях), `yres "600 767"` — вариант для экранов такой высоты.

Условия (`[$WIN32]`, `[$OSX]`...) вычисляются как на ПК: `$WIN32` — любой ПК. Шрифт по имени
берёт вариант, чей `yres` подходит экрану, иначе вариант без `yres`, иначе первый. Шрифты HUD
пропорциональные: если ни один `yres` не подходит, вариант без `yres` (или первый)
растягивается с экрана высотой 480 пикселей на настоящий (`tall`, `blur` и `scanlines` ×
высота экрана / 480).

`scripts/HudLayout.res` — где стоят элементы HUD: блоки `HudHealth`, `HudSuit`, `HudAmmo`,
`HudAmmoSecondary` с `xpos`, `ypos`, `wide`, `tall`, `visible` и местами надписи, числа и
малого числа внутри (`text_xpos`/`text_ypos`, `digit_xpos`/`digit_ypos`,
`digit2_xpos`/`digit2_ypos`). Единица — пиксель экрана высотой 480, на экране высотой 1080 она
равна 2,25 пикселя. Координата — число от левого или верхнего края, `r150` — от правого или
нижнего, `c-20` — от центра. Чего в файле нет, берётся из раскладки Half-Life 2 в том виде, в
каком её оставила GMod.

Реализация: `gmod-lua::surface` (шрифты схем), `gmod-lua::hud` (раскладка и цвета HUD).

## `gameinfo.txt` и `cfg/mount.cfg`

`GameInfo/FileSystem/SearchPaths` — строки вида `ids  путь`:
* `ids` — ID путей поиска через `+`;
* путь задаётся от папки установки, может начинаться с `|all_source_engine_paths|` (папка
  установки) или `|gameinfo_path|` (папка `gameinfo.txt`);
* `.vpk` на конце — пак по базовому имени (`garrysmod.vpk` → `garrysmod_dir.vpk`);
* `/*` на конце — каждая подпапка отдельно.

`cfg/mount.cfg` — `"mountcfg" { "<имя>" "<папка игры>" }`. Подключаются паки `*_dir.vpk` из
папки, затем сама папка.

Реализация: `gmod-fs::gameinfo`, порядок — `gmod-fs::mount` (см.
[ARCHITECTURE.md](ARCHITECTURE.md#файловая-система)).

## Zip — pakfile карт

Карта носит с собой материалы, модели и звуки в zip внутри себя (ламп 40). Каталог zip лежит
в конце: запись «конец каталога» (`0x06054B50`) указывает на центральный каталог, в нём —
записи файлов (`0x02014B50`) со смещениями локальных заголовков (`0x04034B50`), за которыми
идут байты файла.

* Методы: 0 — без сжатия, 8 — DEFLATE (RFC 1951), 14 — LZMA. Последний пишет
  `bspzip -repack`: перед потоком 2 байта версии, `u16` размер свойств (5) и сами свойства.
* В pakfile смещения бывают отсчитаны и от начала zip, и от начала карты. Сдвиг — разница
  между тем, где каталог лежит на самом деле, и тем, где он записан.
* ZIP64 не поддерживается: в картах его нет.

Реализация: `gmod-fs::zip` (zip можно и смонтировать, как пак), `gmod-fs::inflate`,
`gmod-fs::lzma`. Проверено на pakfile настоящей карты: 2772 файла в LZMA, CRC-32 сошлись.

## BSP — карты

Заголовок (1036 байт): `"VBSP"`, `i32` версия (19–21; у GMod — 19 и 20), 64 записи лампов и
`i32` ревизия карты. Запись лампа — `u32` смещение, `u32` длина, `u32` версия и `u32` размер
после распаковки (0 — ламп не сжат). В версии 21 из L4D2 первые три поля переставлены: версия,
смещение, длина; какой порядок у карты, видно по тому, что из него получается.

Сжатый ламп начинается с `"LZMA"`, `u32` размера после распаковки, `u32` размера потока и 5
байт свойств LZMA, за ними — поток. Распакованный ламп не больше 256 МБ: карта с сервера —
чужой файл.

| Ламп | Что | Запись, байт |
|---|---|---|
| 0 | энтити: текст `{ "ключ" "значение" … }` | — |
| 1 | плоскости: нормаль, расстояние, тип | 20 |
| 2 | texdata: отражаемость, имя текстуры, размеры | 32 |
| 3 | вершины | 12 |
| 4 | видимость: кластеры, PVS и PAS | — |
| 5 | узлы деревьев BSP: плоскость, два потомка, границы | 32 |
| 6 | texinfo: векторы текстуры и световой карты, флаги, texdata | 72 |
| 7, 58 | фейсы LDR и HDR | 56 |
| 8, 53 | световые карты LDR и HDR | 4 на люксель |
| 10 | листья: содержимое, кластер, границы, свои браши | 32; 56 в версии 0 лампа |
| 12 | рёбра: два `u16` индекса вершин | 4 |
| 13 | surfedges: `i32` номер ребра, знак — направление | 4 |
| 14 | модели: мир (0) и браш-энтити | 48 |
| 17 | браши листьев: `u16` номер браша | 2 |
| 18 | браши: первая сторона, число сторон, содержимое | 12 |
| 19 | стороны брашей: плоскость, texinfo, дисплейсмент, скос | 8 |
| 20 | области: `i32` число порталов, `i32` первый портал | 8 |
| 21 | порталы областей: `u16` ключ (`portalnumber` у `func_areaportal`), `u16` область по ту сторону, `u16`×2 вершины обрезки, `i32` плоскость | 12 |
| 26, 33 | дисплейсменты и их вершины | 176, 20 |
| 35 | game lump | — |
| 40 | pakfile | — |
| 42 | кубмапы | 16 |
| 43, 44 | имена текстур и таблица смещений к ним | —, 4 |

Видимость (ламп 4) пишет `vvis`: `i32` число кластеров, для каждого `i32` смещение строки PVS
и `i32` смещение строки PAS от начала лампа, затем сами строки. В строке по биту на кластер
(младший бит первого байта — кластер 0), сжатие — по нулям: нулевой байт и за ним байт, сколько
нулевых байт он заменяет. PVS кластера — какие кластеры из него могут быть видны, PAS — какие
слышны (видимые из видимых). Кластер листа — в самом листе (ламп 10), −1 — ни в каком (твёрдое,
вне мира). Карта без `vvis` лампа не имеет: всё видно отовсюду; точка вне кластеров тоже видит
всё.

Модель 0 — мир, остальные принадлежат брашевым энтити (`"model" "*N"`: двери, `func_brush`).
Вершины такой модели записаны относительно `origin` энтити; на место её ставят поворот по
`angles` (тангаж, рыскание, крен) и перенос в `origin`.

Фейс: `u16` плоскость, `u8` сторона, `u8` на узле, `i32` первое ребро, `i16` число рёбер,
`i16` texinfo, `i16` дисплейсмент (−1 — нет), `i16` туман, 4 `u8` стиля света, `i32` смещение
световой карты (−1 — нет), `f32` площадь, `i32`×2 начало и `i32`×2 размер световой карты
(в люкселях минус один), `i32` исходный фейс, `u16`×2 примитивы, `u32` группы сглаживания.
Вершины фейса — по surfedges: ребро с положительным номером берётся от первой вершины, с
отрицательным — от второй. Если смотреть на лицевую сторону, вершины идут по часовой стрелке.
Плоскость фейса уже смотрит туда же, куда он сам: плоскости хранятся парами (чётная и
перевёрнутая нечётная), и «сторона» лишь повторяет чётность номера. Переворачивать нормаль по
ней не нужно. На проверенной карте так у всех фейсов, кроме 14 вырожденных (площадь нулевая
или меньше единицы).

Координаты: `u = (dot(p, s.xyz) + s.w) / ширина текстуры`, так же `v`. Для световой карты —
те же формулы с векторами световой карты, минус начало, в люкселях.

Световая карта — `(w + 1) × (h + 1)` образцов ColorRGBExp32: три `u8` и `i8` порядок, цвет
`c · 2^e / 255`. У фейсов с флагом `BUMPLIGHT` подряд идут 4 страницы (обычная и три для
направлений нормалей), сейчас берётся первая.

Дисплейсмент: сетка `(2^power + 1)²` вершин над четырёхугольным фейсом.
* Сетка начинается с угла фейса, ближайшего к `start_position`; это угол 0, дальше углы
  идут по порядку вершин фейса.
* Строки идут от угла 0 к углу 1, вершины в строке — от ребра 0–1 к ребру 3–2.
* Вершина — точка на фейсе плюс `direction × distance`; `alpha` 0–255 смешивает две текстуры
  (`WorldVertexTransition`).
* Треугольники в клетках чередуют диагональ, как в движке.

Ориентация проверена на настоящей карте: швы соседних дисплейсментов сходятся (54% сдвинутых
краевых точек совпадают с соседями; при транспонированной сетке — 7%).

### Что в карте твёрдое

У каждой модели — мира и каждой брашевой энтити — своё дерево BSP, от её `head_node`.

* Узел: `i32` плоскость, `i32`×2 потомка (сначала спереди от плоскости, потом позади; `≥ 0` —
  узел, `< 0` — лист номер `−1 − n`), `i16`×3 и `i16`×3 границы, `u16` первая грань, `u16`
  число граней, `i16` область, 2 байта выравнивания. Компилятор пишет узел раньше его потомков,
  так что потомок-узел всегда идёт после родителя. Дерево, где это не так, считается битым: в
  нём мог бы оказаться цикл.
* Лист: `u32` содержимое, `i16` кластер видимости, `u16` с областью (9 бит) и флагами (7 бит),
  границы, `u16`×2 грани листа, `u16`×2 браши листа (диапазон лампа 17), `i16` вода. В версии
  0 лампа (карты BSP 19) перед выравниванием идёт ещё куб окружающего света — 6 ColorRGBExp32,
  и запись занимает 56 байт вместо 32.
* Область листа (area) — номер связной части карты, 0 — нет. Компилятор заливает области по
  открытому пространству, поэтому запечатанная комната 3D-скайбокса (с энтити `sky_camera`:
  `scale`, по умолчанию 16, и свой туман — `fogenable`, `fogcolor`, `fogstart`, `fogend`,
  `fogmaxdensity`) получает свою. Туман мира — энтити `env_fog_controller` с теми же ключами
  (`fogcolor` — `r g b` 0–255 в sRGB; расстояния — в юнитах мира, для скайбокса тоже).
* Браш — выпуклое тело: пространство позади плоскостей всех его сторон, нормали смотрят наружу.
  Сторона: `u16` плоскость, `i16` texinfo (−1 — нет), `i16` дисплейсмент, флаг скоса (в картах
  GMod — `i16`, в поздних играх — `u8` и за ним ещё `u8`). Скосы — плоскости, которые
  компилятор добавляет по осям и вдоль рёбер: коробка, расширенная на браш, упирается в его
  рёбра так же, как в грани. Своих граней у скосов нет, лучу они не нужны.

Содержимое (`CONTENTS_` в Lua GMod) — флаги: `SOLID` 0x1, `WINDOW` 0x2, `GRATE` 0x8, `SLIME`
0x10, `WATER` 0x20, `MOVEABLE` 0x4000, `PLAYERCLIP` 0x10000, `MONSTERCLIP` 0x20000, `DETAIL`
0x8000000, `LADDER` 0x20000000 и другие. Трассировка останавливается на брашах, чьё
содержимое пересекается с её маской: `MASK_SOLID` — это `SOLID | MOVEABLE | WINDOW | MONSTER |
GRATE`, `MASK_PLAYERSOLID` — то же и `PLAYERCLIP`.

Дисплейсмент — поверхность, а не браш: openGMOD сталкивает с его треугольниками (теми же, что
рисуются) и только с лицевой стороны; содержимое берётся из `contents` дисплейсмента. Брашевая
энтити стоит в своём `origin`, повёрнутая на `angles`. Триггеры, `func_illusionary`,
`func_clip_vphysics` и подобные не твёрдые; `func_brush` с `Solidity` 1 — тоже.

Пока проверено на тестовых картах, записанных по этому описанию. На настоящих картах проверку
делает `gmod-check`: строка `Collision`.

Game lump — каталог: `i32` число записей; запись — `u32` ID, `u16` флаги, `u16` версия, `i32`
смещение от начала файла, `i32` длина. Флаг 1 — ламп сжат LZMA (тот же блок, что выше), длина
тогда — размер после распаковки. Каталог заканчивается пустой записью, её смещению верить
нельзя (бывает 0).

`sprp` — статические пропы: `i32` число и столько 128-байтных путей моделей, `i32` число и
столько `u16` листьев, `i32` число и записи пропов. Первые 56 байт записи одинаковы во всех
версиях (позиция, углы, модель, листья, твёрдость, флаги, скин, дальность исчезновения, точка
освещения); размер записи — по версии: 4 — 56, 5 — 60, 6 — 64, 7 и 8 — 68, 9 — 72, 10 — 76,
11 и 12 — 80.

Ламп 45 — оверлеи (`info_overlay`), записи по 352 байта: `i32` id, `i16` texinfo, `u16` число
граней (младшие 14 бит) и порядок отрисовки (старшие 2), 64 `i32` грани, `f32`×2 U и `f32`×2 V
(диапазоны координат текстуры), 4 точки `f32`×3 (углы в плоскости оверлея; в третьих числах
первых трёх — ось U), `f32`×3 origin, `f32`×3 нормаль. V = нормаль × U. Оверлей лежит на своих
гранях: его четырёхугольник переносится вдоль нормали на плоскость каждой грани и обрезается
по её рёбрам. Раскладка проверена только на синтетических картах.

Реализация: `gmod-bsp`. Проверено на настоящей карте TF2: 23 984 фейса, 757 дисплейсментов,
1211 статических пропов (`sprp` v10), LZMA-сжатые лампы и game lumps.

## VTF — текстуры

Заголовок:

| Смещение | Поле |
|---|---|
| 0 | `"VTF\0"` |
| 4 | `u32` версия: 7 и 0–5 |
| 12 | `u32` размер заголовка |
| 16 | `u16` ширина и высота, `u32` флаги, `u16` число кадров, `u16` первый кадр |
| 32 | `f32`×3 отражаемость (до и после — по 4 байта выравнивания) |
| 48 | `f32` масштаб бампа, `i32` формат пикселей, `u8` число мипов |
| 57 | `i32` формат миниатюры (−1 — нет), `u8` её ширина и высота |
| 63 | с 7.2: `u16` глубина (объёмные текстуры) |
| 68 | с 7.3: `u32` число ресурсов, с 80 — записи по 8 байт |

Запись ресурса: 3 байта тега, байт флагов и `u32` — смещение данных ресурса или, с флагом 2,
само значение. `01 00 00` — миниатюра, `30 00 00` — изображение; `CRC`, `LOD`, `TSO`, `KVD` —
настройки.

До 7.2 за заголовком идёт миниатюра (маленькая DXT1), за ней изображение; с 7.3 их находят по
ресурсам. Изображение идёт от самого маленького мипа к самому большому; внутри мипа — по кадрам,
в кадре — по граням, в грани — по слоям глубины. Размер мипа — `max(1, размер >> уровень)`.

Кубмапа (флаг `ENVMAP`, `0x4000`) — 6 граней. До 7.5 за ними идёт седьмая, сферическая карта,
если первый кадр не `0xFFFF`. На деле её может и не быть, поэтому число граней сверяется с
размером файла. В HDR-кубмапах проверенной карты седьмая грань не заполнена.

Форматы пикселей — номера 0–29: `RGBA8888`, `ABGR8888`, `RGB888`, `BGR888`, `RGB565`, `I8`,
`IA88`, `P8`, `A8`, `RGB888_BLUESCREEN`, `BGR888_BLUESCREEN`, `ARGB8888`, `BGRA8888`, `DXT1`,
`DXT3`, `DXT5`, `BGRX8888`, `BGR565`, `BGRX5551`, `BGRA4444`, `DXT1_ONEBITALPHA`, `BGRA5551`,
`UV88`, `UVWQ8888`, `RGBA16161616F`, `RGBA16161616`, `UVLX8888`, `R32F`, `RGB323232F`,
`RGBA32323232F`. Компоненты в имени перечислены от первого байта (у 16-битных — от младших
битов): `BGRA8888` — байты B, G, R, A; в `BGR565` синий в битах 0–4, красный в 11–15. `*_BLUESCREEN`
— чистый синий прозрачен. `P8` без палитры не показать.

DXT — сжатие S3TC блоками 4×4 (BC1–BC3 в Direct3D): два цвета RGB565 и 2 бита выбора на пиксель
из четырёх цветов (два крайних и два между ними). В DXT1, если первый цвет не больше второго,
цветов три, а четвёртый — прозрачный чёрный. DXT3 добавляет 4 бита альфы на пиксель; DXT5 — две
крайние альфы, шесть между ними (или четыре, 0 и 255) и 3 бита выбора на пиксель.

Реализация: `gmod-material::vtf`, `gmod-material::decode`. Проверено на 286 текстурах (7.1–7.4,
DXT1/5, BGRA8888, BGRA4444, RGB(A)888, BGR888, RGBA16161616F, кубмапы с 7 гранями): все 7815
изображений декодируются; DXT совпадает с декодером ImageMagick с точностью до 1 (округление
промежуточных цветов).

## VMT — материалы

KeyValues с одним блоком верхнего уровня; его имя — шейдер, внутри — параметры:

```
"LightmappedGeneric"
{
    "$basetexture" "concrete/concretefloor001a"
    "$surfaceprop" "concrete"
}
```

* Имена без учёта регистра; из двух одинаковых считается первое.
* Текстуры названы путём от `materials/` без `.vtf`, бывает с `\`.
* Числа — ведущее число значения; векторы и цвета — `[1 .5 0]`, `{255 128 0}` (0–255) или одно
  число на все три.
* Блоки с условием на уровень DirectX (`">=dx90"`, `"<dx90_20b"`) добавляют свои параметры поверх
  остальных, если условие выполнено. openGMOD отвечает как железо DirectX 9 (`dx95`).
* Блоки с именем шейдера и суффиксом (`LightmappedGeneric_DX8`) — настройки для старого железа,
  не используются.
* Параметр с условием: `"hdr?$envmaptint"`, `"!srgb?$color"`, `"GPU>=2?$detail"`. Выполнены
  `hdr`, `srgb` и `GPU>=` до 3; не выполнены `ldr`, `lowfill`, консоли и всё незнакомое.
* `Proxies` — код, меняющий параметры во время игры (анимация, прокрутка).

Патч-материал берёт другой материал и меняет его:

```
"patch"
{
    "include" "materials/glass/glasswindow001a.vmt"
    "replace" { "$envmap" "maps/mymap/c1984_352_32" }
}
```

`insert` задаёт параметры, добавляя недостающие; `replace` меняет только существующие. Патчи
могут включать патчи (не глубже 8). Карты кладут такие патчи в pakfile, чтобы дать материалу
ближайшую к грани кубмапу.

Блок `Proxies` — код, который меняет параметры, пока идёт игра: `"Proxies" { "Sine" {
"sineperiod" "2" "sinemin" "0" "sinemax" "1" "resultvar" "$alpha" } }`. Прокси выполняются
по порядку каждый кадр и передают значения через параметры, в том числе через компоненту
вектора (`$color[1]`); число на входе может быть именем параметра. `AnimatedTexture` листает
кадры VTF (`animatedtextureframerate`, по умолчанию 15), `TextureScroll` сдвигает
преобразование координат (`texturescrollrate`, `texturescrollangle`), `TextureTransform`
собирает его из центра, масштаба, поворота и сдвига.

Реализация: `gmod-material::vmt`, загрузка с патчами — `gmod_material::load_material`, прокси —
`gmod-material::proxy`.

## MDL, VVD, VTX — модели

Модель — три файла, скомпилированные вместе; у всех одна контрольная сумма.

`.mdl` — заголовок `"IDST"`, версия 44–49 (у GMod почти всегда 48), дальше — счётчики и смещения
таблиц. Имена — смещения строк, обычно от начала записи, в которой они лежат.

| Смещение | Поле |
|---|---|
| 8 | `i32` контрольная сумма |
| 12 | имя, 64 байта |
| 80 | точки глаз и освещения, hull и рамка вида (`f32`×3 каждая) |
| 152 | `i32` флаги |
| 156 | кости: число, смещение (записи по 216 байт) |
| 172 | наборы хитбоксов: число, смещение (записи по 12 байт: имя, число и смещение коробок по 68 байт — кость, группа попадания, min и max в пространстве кости, имя) |
| 180 | анимации: число, смещение (записи по 100 байт; см. «Анимации моделей») |
| 188 | последовательности: число, смещение (записи по 212 байт) |
| 204 | текстуры: число, смещение (записи по 64 байта) |
| 212 | папки текстур: число, смещение таблицы смещений строк |
| 220 | скины: текстур в скине, число скинов, смещение таблицы `u16` |
| 232 | части тела: число, смещение (записи по 16 байт) |
| 240 | точки крепления (attachments): число, смещение (записи по 92 байта) |
| 300 | параметры поз: число, смещение (записи по 20 байт) |
| 308 | свойство поверхности, `$keyvalues` (смещение, размер), масса (328) |
| 336 | включаемые модели: число, смещение (записи по 8 байт: метка, путь) |
| 348 | блоки анимаций: имя файла `.ani` (смещение строки), число блоков, смещение (по 8 байт: начало, конец) |

* Материал текстуры ищется в каждой папке по очереди: `materials/<папка><имя>.vmt`.
* Скин — таблица «слот → текстура»; меш ссылается на слот.
* Часть тела (16 байт: имя, число моделей, `base`, смещение) держит модели, из которых видна одна:
  номер модели — `body / base % число моделей`.
* Модель (148 байт): имя, число и смещение мешей, число вершин и смещение первой — в байтах
  от начала вершин `.vvd` (по 48 байт на вершину).
* Меш (116 байт): слот материала, число вершин и первая вершина от первой вершины модели.
* `$keyvalues` модели (смещение 308) — текст KeyValues, у скомпилированных моделей обёрнутый в
  блок `mdlkeyvalue { ... }`. Блок `prop_data` описывает, как проп ломается: `"base"` — класс из
  `scripts/propdata.txt` игры (здоровье, множители урона `dmg.bullets`, `dmg.club`,
  `dmg.explosive`), свои `health`, `explosive_damage`, `explosive_radius` важнее класса.

`.vvd` — `"IDSV"`, версия 4, контрольная сумма, число уровней детализации, `i32`×8 вершин на
уровень, число и смещение fixup-ов, смещения вершин и тангенсов. Вершина — 48 байт: 3 веса костей
(`f32`), 3 номера костей и их число (байты), позиция, нормаль, текстурные координаты. Если
fixup-ы есть, уровень `L` собирается из диапазонов (`i32` уровень, первая вершина, число) с
уровнем не меньше `L`; меши модели считают вершины на уровне 0.

`.vtx` (`.dx90.vtx`) — версия 7, заголовок 36 байт, затем вложенные таблицы: части тела (8 байт)
→ модели (8) → уровни детализации (12: число мешей, смещение, расстояние переключения) →
меши (9) → группы полос (25 байт) → вершины (9 байт: данные костей и `u16` номер вершины в меше),
индексы `u16` в вершины группы и полосы (27 байт: списки или ленты треугольников). Смещения
считаются от записи, в которой лежат. Компиляторы поновее добавляют к группам и полосам по два
поля (33 и 35 байт); файл читается той раскладкой, которая к нему подходит.

Реализация: `gmod-model`. Проверено на 15 моделях (пропы TF2 из карты и шляпа из TTT): все
строятся, габариты сетки сходятся с hull.

## Анимации моделей

Что модель проигрывает на своих костях, лежит в том же `.mdl`, а у больших моделей — частью в
файле `.ani` рядом (блоки анимаций). Модель игрока обычно своих анимаций почти не имеет: она
включает модели с анимациями (`models/m_anm.mdl` и др.), и их последовательности играются на её
костях с теми же именами.

**Кость** (216 байт), кроме имени, родителя, позиции и кватерниона покоя (32, 44) и матрицы
`pose_to_bone` (96): углы Эйлера покоя в радианах (`f32`×3 по смещению 60), масштабы значений
анимаций для позиции (72) и углов (84), флаги (160), смещение имени свойства поверхности (176),
`i32` содержимое (180). Углы Эйлера и кватернион покоя описывают один поворот: сначала вокруг x,
потом y, потом z (q = qz·qy·qx). Проверено на 33 моделях: расхождение не больше 10⁻⁷.

**Анимация** (100 байт):

| Смещение | Поле |
|---|---|
| 0 | `i32` смещение от записи к началу файла (отрицательное) |
| 4 | смещение имени (`@idle01`) |
| 8 | `f32` кадров в секунду |
| 12 | `i32` флаги (1 — зациклена, 4 — дельта) |
| 16 | `i32` число кадров |
| 20 | движение по земле: число, смещение (записи по 44 байта) |
| 52 | `i32` номер блока `.ani` (0 — сам `.mdl`), `i32` смещение кадров |
| 80 | секции: смещение таблицы, `i32` кадров в секции (0 — без секций) |

* Без секций кадры лежат по смещению от записи анимации (блок 0) или от начала блока в `.ani`.
* С секциями таблица (по 8 байт: блок, смещение) держит `кадры / в секции + 2` записей: секция `s`
  — кадры с `s·n`, а последний кадр длинной анимации лежит отдельно, в последней записи. Каждый
  кадр берётся из своей секции по этому правилу.
* Движение (44 байта): последний кадр отрезка, флаги, скорости в начале и конце, угол,
  направление и куда модель пришла к концу отрезка (`f32`×3 по смещению 32) — отсюда скорость по
  земле: путь за цикл × циклов в секунду.

**Кадры** — список записей, по одной на каждую кость, которую анимация двигает: `u8` номер
кости, `u8` что хранится, `i16` смещение до следующей записи (0 — последняя). Сразу за этими
четырьмя байтами — данные поворота, потом позиции:

| Бит | Что |
|---|---|
| 0x20 | поворот — кватернион в 64 битах, для всех кадров: x, y, z по 21 биту (`(v − 1048576) / 1048576,5`), старший бит — знак w |
| 0x02 | поворот — кватернион в 48 битах: `u16` x и y (`(v − 32768) / 32768`), 15 бит z (`(v − 16384) / 16384`), бит знака w |
| 0x08 | поворот — три угла, меняющиеся по кадрам: `i16`×3 смещения потоков значений (0 — нет потока) |
| 0x01 | позиция — три half float, для всех кадров |
| 0x04 | позиция — три потока значений |
| 0x10 | дельта: значения не прибавляются к покою кости |

w кватерниона — `√(1 − x² − y² − z²)` со знаком из бита. Поток значений — серии: байт «сколько
значений хранится», байт «сколько кадров серия покрывает», затем хранимые `i16`; кадры серии
после хранимых повторяют последнее значение. Угол — значение × масштаб углов кости + её угол
покоя (кроме дельты), позиция — так же с масштабом позиции. Между кадрами повороты
интерполируются по сфере, позиции — линейно. Запись с номером кости, которой у модели нет,
ничего не двигает: анимация, не двигающая ни одной кости, состоит из одной записи для кости 255.

**Последовательность** (212 байт) — то, что играет энтити:

| Смещение | Поле |
|---|---|
| 4, 8 | смещения метки (`idle01`) и имени активности (`ACT_VM_IDLE`) |
| 12 | `i32` флаги: 1 — зациклена, 4 — дельта, 0x10 — дельта в пространстве кости, 0x800 — заменяет одноимённую из модели, включённой раньше |
| 20 | `i32` вес активности (насколько чаще выбирается среди последовательностей той же активности) |
| 24 | события: число, смещение (по 80 байт: `f32` цикл, `i32` номер, `i32` тип, 64 байта параметров, смещение имени) |
| 32 | рамка (`f32`×6) |
| 60 | смещение таблицы `i16` номеров анимаций сетки |
| 68 | `i32`×2 размер сетки по двум параметрам позы, `i32`×2 номера параметров, `f32`×2 начала и `f32`×2 концы их диапазонов в сетке |
| 104 | `f32` время вплывания и уплывания |
| 148 | слои: число, смещение (по 24 байта: `i16` последовательность, `i16` параметр позы, `i32` флаги, `f32` начало, пик, хвост, конец) |
| 156 | смещение весов костей (`f32` на кость; 0 — все 1) |
| 172 | `$keyvalues` последовательности (смещение, размер) |

* Анимации сетки смешиваются по значениям параметров позы: по первому параметру — вдоль строки
  сетки, по второму — от строки к строке; значение параметра в его единицах переводится в долю
  диапазона последовательности, и берутся две (или четыре) соседние анимации с весами.
* Слой играется поверх своей последовательности: если начало равно концу — всё время, иначе
  его вес растёт от начала к пику, держится до хвоста и падает к концу — по циклу или по значению
  параметра позы (флаг 0x4000); слой с флагом 0x1000 накладывается на позу самой
  последовательности до смешивания.
* Дельта прибавляется к тому, что под ней: поворот `дельтаʷ · поворот` (у 0x10 — справа),
  позиция — сложением.

**Параметр позы** (20 байт): смещение имени, `i32` флаги, `f32` начало, конец и период для углов,
которые «заворачиваются» (360). Энтити хранит его от 0 до 1 по диапазону; поначалу он стоит на
значении 0 своих единиц.

**`.ani`** — `"IDAG"`, версия, контрольная сумма (на практике 0), имя, длина; дальше данные
блоков, чьи границы даёт таблица блоков `.mdl` (блок 0 — сам `.mdl`, его диапазон пустой).

Реализация: `gmod-model::anim` (чтение), `gmod-model::pose` (риг с включаемыми моделями,
поза, матрицы). Проверено на 38 моделях двух публичных аддонов (оружие v_ и c_ с секциями,
модели игроков с включаемыми моделями, модель с `.ani`, NPC): все кадры читаются, поза покоя,
умноженная на `pose_to_bone` из файла, даёт единичные матрицы с точностью 10⁻⁵, кости движутся от
кадра к кадру плавно; на своей установке — `gmod-check`, строка `Animations`.

## VHV — свет статических пропов

`sp_<n>.vhv` и `sp_hdr_<n>.vhv` в pakfile карты, `n` — номер пропа: свет, посчитанный VRAD для
каждой вершины. Заголовок 40 байт: `i32` версия (2), `u32` контрольная сумма модели, флаги,
`u32` байт на вершину (4), число вершин, `i32` число мешей и 4 пустых слова. Затем по 28 байт на
меш: уровень детализации, число вершин, смещение цветов. Меши идут в порядке вложенности `.vtx`.

* Цвета привязаны к «аппаратным» вершинам — к вершинам групп полос `.vtx` в их порядке, а не к
  вершинам `.vvd`: у тачки из TF2 на уровне 0 их 1570 из 1733.
* Цвет — байты B, G, R, A; это линейный свет, 255 — единица. Проверено на 454 пропах карты TF2:
  отношение к световой карте пола вокруг пропа — 0,9 при таком чтении, а первый байт следует за
  синей составляющей света.

Реализация: `gmod-model::vhv`.

## PHY — физические модели

`.phy` рядом с `.mdl`: то, чем модель сталкивается, её масса, у рэгдоллов — суставы. Заголовок
16 байт: `i32` его размер, `i32` 0, `i32` число твёрдых тел, `i32` контрольная сумма модели
(та же, что в `.mdl`; физика от другой сборки модели не годится). Дальше каждое тело — `i32`
размер и столько байт данных столкновения, а после всех тел — текст.

Данные тела — сжатая поверхность IVP (compact surface). У моделей, собранных с 2006 года, перед
ней заголовок 28 байт: `"VPHY"`, `i16` версия (0x100), `i16` тип (0 — многогранники; другие не
встречаются), `i32` размер поверхности, `f32`×3 площади для сопротивления воздуха, `i32` размер
карты осей. У старых моделей данные начинаются прямо с поверхности.

| Что | Байт | Поля |
|---|---|---|
| поверхность | 48 | центр масс, инерция, радиус (`f32`×7); `i32`: 8 бит флагов и 24 — размер; `i32` смещение корня дерева от начала поверхности; `i32`×3, последнее — `"IVPS"` |
| узел дерева | 28 | `i32` смещение правого потомка (0 — лист; левый — следующий узел), `i32` смещение куска, оба от узла; центр, радиус, размеры |
| кусок (ledge) | 16 | `i32` смещение точек от куска, `i32` данные клиента, `u32`: 2 бита «есть дети», 2 — «сжатый», 4 пустых, 24 — размер в 16-байтных единицах; `i16` число треугольников, `i16` пусто; дальше треугольники |
| треугольник | 16 | `u32`: номер (12 бит), pierce-номер (12), материал (7), «виртуальный» (1); 3 ребра по `u32`: номер начальной точки (16 бит), смещение противоположного ребра (15, со знаком), «виртуальное» (1) |
| точка | 16 | `f32`×3 и ещё `f32`, здесь не нужный |

* Тело — выпуклые куски в листьях дерева. Внутренний узел тоже может указывать на кусок — на
  оболочку всего, что под ним; это не часть формы, и такие куски пропускаются.
* Точки общие для всех кусков тела; кусок берёт те, на которые ссылаются его треугольники.
  Обход дерева всегда идёт вперёд по данным: дерево с правым потомком позади узла — битое.
* IVP считает в метрах, оси повёрнуты: точка IVP (x, y, z) — это (x, z, −y) / 0,0254 в юнитах
  модели. Обход треугольников в файле здесь не важен: openGMOD разворачивает их наружу.
* Тело лежит в пространстве своей кости: у пропа из одной кости это пространство модели, у
  рэгдолла — кости своей части.

Текст — блоки `имя { "ключ" "значение" ... }`: `solid` на каждое тело (`index` — номер тела,
`name` — кость, `mass` в килограммах, `surfaceprop`, `damping`, `rotdamping`, `inertia`,
`volume`), `editparams` (`totalmass`, `concave`), `ragdollconstraint` (`parent`, `child`,
пределы `xmin`…`zmax` в градусах и трение `xfriction`…), `collisionrules`, `break` и другие.

* Пределы `ragdollconstraint` заданы вокруг осей кости ребёнка в позе покоя: x идёт вдоль кости
  (поворот вокруг неё — скручивание), y и z — изгибы; колено, например, гнётся вокруг z от −12
  до 145. Все пределы 0 — часть приварена к родителю.
* `inertia` (у кусков рэгдоллов обычно 10) умножает момент инерции тела.
* `collisionrules`: `"selfcollisions" "0"` — части рэгдолла не сталкиваются друг с другом
  вовсе; `"collisionpair" "a,b"` — эти два тела сталкиваются (остальные — нет). Без блока
  openGMOD сталкивает все части, кроме соединённых суставом и перекрытых в покое.
* Проверено на шести моделях рэгдоллов из публичного аддона: куски, расставленные матрицами
  «кость → модель» покоя своих костей, складываются в фигуру модели.

Статический проп карты сталкивается так, как сказано в его поле `solid`: 0 — никак, 2 (и 3, 4) —
габаритной коробкой модели (hull из `.mdl`), повёрнутой вместе с пропом, 6 — своей физической
моделью; без `.phy` такой проп не твёрдый.

Реализация: `gmod-model::phy`, оболочки в столкновениях — `gmod-bsp::collision::Hull`. Пока
проверено на тестовых файлах, записанных по этому описанию; на настоящих — `gmod-check`,
строки `Physics` и `Collision`.

## Протокол openGMOD

Свой протокол серверов и клиентов openGMOD (`gmod-net`, `gmod-app::proto`); с протоколом
Source не совместим. Числа — little-endian.

### Пакеты (`gmod-net`)

UDP-датаграмма до 1200 байт: `OGMN`, байт вида, дальше по виду. Версия протокола — 2.

| Вид | Кто шлёт | Содержимое |
|---|---|---|
| 1 `CONNECT` | клиент | `u16` версия протокола, `u64` случайное число попытки (соль), нули до 1200 байт |
| 8 `CHALLENGE` | сервер | соль, ключ сервера для этого соединения (X25519, 32 байта), ключ самого сервера (Ed25519, 32 байта), подпись (64 байта) строки `openGMOD challenge` + соль + ключ соединения |
| 9 `JOIN` | клиент | соль, ключ клиента для соединения (X25519), ключ самого игрока (Ed25519), подпись (64 байта) стенограммы, затем запечатанное приветствие (до 1000 байт) |
| 2 `ACCEPT` | сервер | соль, `u64` номер соединения (случайный), затем запечатанный ответ (до 1000 байт) |
| 3 `DENY` | сервер | соль, причина (UTF-8 до конца пакета) |
| 4 `DATA` | обе стороны | `u64` номер соединения, `u64` номер пакета в шифре; запечатано: `u16` номер пакета, `u16` номер последнего пришедшего (`0xffff` — ещё нет), `u32` номер надёжного куска, до которого пришло всё, `u8` число диапазонов (до 8) и диапазоны пришедших раньше кусков (`u32` первый, `u16` сколько), затем записи |
| 5 `DISCONNECT` | обе стороны | `u64` номер соединения, `u64` номер пакета в шифре; запечатано: причина (UTF-8) |
| 6 `QUERY` | кто угодно, без соединения | `u64` случайное число вопроса, нули до 1200 байт |
| 7 `INFO` | сервер | `u64` число вопроса, что сервер говорит о себе (до 1187 байт) |
| 12 `HEARTBEAT` | сервер мастер-серверу | `u16` версия протокола, нули до 1200 байт |
| 10 `LIST` | кто угодно мастер-серверу | `u64` случайное число вопроса, `u16` версия протокола, `u32` номер первого нужного сервера, нули до 1200 байт |
| 11 `SERVERS` | мастер-сервер | `u64` число вопроса, `u32` сколько серверов всего, `u32` номер первого на странице, адреса: `u8` 4 или 6, 4 или 16 байт адреса, `u16` порт — сколько поместится в пакет |

«Запечатано» — ChaCha20-Poly1305: шифр и 16 байт метки в конце; всё, что до запечатанного,
идёт открыто, но тоже под меткой (как связанные данные). Nonce — 4 нулевых байта и `u64` номер
пакета; приветствие и ответ сервера — номер 0, пакеты соединения — с 1, у каждой стороны свой
ключ. Стенограмма — строка `openGMOD join`, соль, ключ сервера, его ключ соединения, ключ
игрока, его ключ соединения. Ключи соединения — HKDF-SHA256 общего секрета X25519 (соль HKDF —
строка `openGMOD connection keys`, info — `client to server` или `server to client` и
стенограмма).

Рукопожатие: `CONNECT` → `CHALLENGE` → `JOIN` → `ACCEPT` или `DENY`. Клиент проверяет подпись
сервера и, если уже играл на этом адресе, — что ключ сервера тот же; сервер проверяет подпись
игрока. На `JOIN` может ответить только тот, кто получил `CHALLENGE`, — подделанный адрес
отправителя ничего не даёт; `CONNECT` короче целого пакета (кроме чужой версии протокола)
остаётся без ответа, а ответ на него всегда короче. Новых вызовов (`CHALLENGE`) — не больше
200 в секунду: каждый стоит серверу пары ключей и подписи. Пакет соединения, который не
открылся (подделан, изменён, не этого соединения) или с номером, который уже приходил (окно из
1024 последних), отбрасывается.

Записи `DATA`, подряд до конца пакета:

| Вид | Содержимое |
|---|---|
| 1 надёжный кусок | `u32` номер куска, `u8` 1 — последний кусок сообщения, `u16` длина, байты (до 1000) |
| 2 ненадёжное сообщение | `u16` длина, байты |
| 3 фрагмент ненадёжного | `u16` номер группы, `u8` номер фрагмента, `u8` сколько их, `u16` длина, байты |

Клиент шлёт `CONNECT`, потом `JOIN` каждые 250 мс, пока не получит ответ (всего 10 с); повтор
с той же солью получает тот же ответ. Надёжное сообщение (до 64 МиБ) режется на куски, которые идут
снова, пока не подтверждены, через max(100 мс, 1,5 RTT); получатель держит не больше 4096
кусков впереди ожидаемого и собирает сообщения по порядку. RTT меряется по номеру последнего
пришедшего пакета. Пакет, номер которого уже был (среди последних 1024), отбрасывается целиком.
Сторона, которой нечего сказать, шлёт пустой `DATA` раз в 100 мс; сторона, от которой ничего
нет 15 с, считается ушедшей. Фрагменты ненадёжного сообщения, не собранные за 2 с,
выбрасываются; ненадёжное сообщение — до 255 фрагментов.

`QUERY` короче целого пакета остаётся без ответа: вопрос не меньше любого ответа, так что
сервер нельзя использовать как усилитель трафика с поддельным адресом. Браузер серверов шлёт
`QUERY` на широковещательный адрес (порты 27015–27020) и на адреса из избранного и истории.

Мастер-сервер (`opengmod --master`, UDP-порт 27011; `gmod-net::master`) ведёт список серверов
интернет-вкладки. Сервер раз в минуту шлёт ему `HEARTBEAT` (если `sv_lan` 0 и мастера названы);
мастер отвечает на это `QUERY` на адрес, откуда пришёл `HEARTBEAT`, и вносит сервер в список,
только когда тот ответит `INFO`, — так в списке только живые серверы по их настоящим адресам, а
подделанный адрес получает вопрос не длиннее своего пакета. Сервер без `HEARTBEAT` 5 минут из
списка уходит. Браузер просит список страницами (`LIST` → `SERVERS`, только серверы своей версии
протокола) и опрашивает каждый сервер сам, как в локальной сети. Короткие `HEARTBEAT` и `LIST`
остаются без ответа. Мастер за серверы не ручается: ключ сервера игрок узнаёт при подключении.
Мастеров клиент и сервер берут из `servers/masters.txt` в папке openGMOD (адрес на строку,
порт по умолчанию 27011), выделенный сервер — ещё из `--announce`; по умолчанию мастеров нет.

### Ключи (`gmod-app::keys`)

В папке openGMOD (`~/.opengmod` или `$OPENGMOD_HOME`):

* `identity.key` — ключ игрока, `server.key` — ключ сервера этого компьютера: строки `#` —
  комментарии (в них же открытый ключ), затем зерно Ed25519 — 64 шестнадцатеричные цифры. Файл
  создаётся при первом запуске, читать его может только владелец; чужой или испорченный файл не
  перезаписывается.
* `servers/known.txt` — ключи серверов, на которых играли: строка — адрес (`IP:порт`), пробел,
  ключ (64 шестнадцатеричные цифры). Первый ключ адреса остаётся; сервер с другим ключом не
  подключается, пока строку не удалят.

`SteamID64` игрока — свой, не Steam: `76561197960265728` + номер аккаунта, а номер — первые
4 байта SHA-256 открытого ключа (little-endian, 0 заменяется на 1). `SteamID` из него —
`STEAM_0:номер % 2:номер / 2`, как у GMod.

### Сообщения игры (`gmod-app::proto`)

Каждое сообщение — postcard-сериализация перечисления; первый байт: 0 — как есть, 1 — сжато
DEFLATE (сырой поток). Приветствие клиента — `Hello { version: 1, name }`, ответ сервера —
`Welcome { server, map, gamemode, max_players, allow_cs_lua, loading_url }`. Ответ на `QUERY` —
postcard-сериализация `ServerInfo { name, map, gamemode, title, players, max_players, bots,
version, instance, list }` (без байта сжатия): `instance` — случайное число, выбранное сервером
при старте (сервер, ответивший с нескольких адресов, в списке один раз), `list` — игроки (имя,
фраги, секунды в игре), сколько поместится.

Клиент → сервер (`ToServer`): `Want(пути)`, `Ready`, `Commands { last, commands, ack }`
(ненадёжно: до четырёх последних `UserCmd`, номер последней и номер последнего полученного
снимка), `Command(строка консоли)`, `UserInfo(имя, значение)`, `Net { name, data }`.

Сервер → клиент (`FromServer`): `Files { lua, content }` (путь, размер, CRC-32 каждого файла),
`File { path, offset, size, data }` (куски по 1 МиБ), `FilesSent`, `Joined { player }`,
`Snapshot(SnapshotDelta)` (ненадёжно, если влезает в 255 фрагментов), `Chat`, `Net`,
`Sounds`, `Asked(SendLua | ConCommand | печать в консоль)`.

`SnapshotDelta { seq, baseline, time, command, removed, changed }`: номер снимка; снимок, к
которому дельта (0 — полный); `CurTime` сервера; последняя учтённая команда клиента; индексы
ушедших энтити; новые и изменённые энтити — `(индекс, xor, байты)`, где байты — postcard
`EntityState` целиком или, при `xor`, побайтовый XOR с её байтами в базовом снимке той же
длины. Стороны помнят последние 64 снимка.

## Диалект Lua в GMod

| GLua | Lua |
|---|---|
| `a != b` | `a ~= b` |
| `!a` | `not a` |
| `a && b`, `a \|\| b` | `a and b`, `a or b` |
| `// …`, `/* … */` | комментарии |
| `continue` | переход к следующей итерации цикла |
| `DEFINE_BASECLASS("имя")` | `local BaseClass = baseclass.Get("имя")` |

`DEFINE_BASECLASS` — единственный макрос GMod: его разворачивает сам компилятор, а не Lua.
Разворачивается только вызов-оператор, не поле (`t.DEFINE_BASECLASS`) и не значение.

`continue` — оператор, только если сразу за ним кончается блок (`end`, `else`, `elseif`,
`until`, `;`). Иначе это обычное имя: `t.continue`, `local continue`, `goto continue`.

Как переводит `gmod-glua`:
* в `while` и `for` тело оборачивается в `do … end ::метка::`, а `continue` становится
  `goto метка`;
* в `repeat … until` метка ставится перед `until`. Здесь LuaJIT, как и с родным `continue`,
  не даёт перепрыгнуть объявление `local`.

Номера строк сохраняются, байты строк не меняются, BOM UTF-8 удаляется.
